# 카드 혜택 BEP Agent — 서비스 기획서

> 카드를 여러 장 쓰는 개인이 채팅으로 "이번 달 할인은 얼마고, 이 카드로 얼마까지 써야 하나"를 묻고 바로 답을 받는 카드 혜택 Agent입니다.
> 카드사 약관을 자동으로 내려받아 RAG로 점검하고, 내 카드 사용내역과 함께 보며 월 한도·실적 하한·실적 제외 같은 함정 조건을 약관 원문 근거와 함께 짚어 줍니다.
> 할인액과 사용 한계선(BEP) 계산은 파이썬 코드가 맡아 숫자를 지어내지 않으며, 공개용 데이터는 모두 가상입니다.

## 1. 무엇을 만드나

카드 사용내역과 카드사 약관을 바탕으로, 보유한 카드마다 다음을 알려주는 개인용 Agent를 만든다.

- 이번 달 **예상 할인액**
- 할인을 다 받으려면 **이 카드로 얼마까지 써야 하는지**(BEP), 그 이상은 다른 카드로 옮겨야 한다는 지점
- 광고 할인율 뒤에 숨은 **함정 조건**과 그 약관 원문

> **BEP(손익분기점)란?** 이 서비스에서는 "이 카드로 이만큼 쓰면 받을 수 있는 할인을 다 받는다"는 사용액이다.
> 예) 15% 할인, 월 한도 5,000원이면 BEP는 33,334원이다. 그 이상 쓰는 돈에는 할인이 붙지 않는다.

### 최종 목표: 내 LLM에서 정기 리포트 받기

이 서비스를 Agent로 개발해, 최종적으로는 사용자가 평소 쓰는 **LLM(ChatGPT, Claude 등)에서 정기적으로 카드 리포트를 받는 것**을 목표로 한다. 따로 화면을 열지 않아도 늘 쓰는 대화창에서 결과를 받고, 궁금한 점은 그 자리에서 이어서 묻는다.

- **하루 3번 리포트:** 결제는 매일 일어나므로 리포트도 매일 받는다. 시각은 사용자가 정하며, MCP 서버가 승인내역을 새로 수집한 직후에 만든다.

| 시각 (예) | 리포트 | 담는 내용 |
|---|---|---|
| 아침 08:00 | **오늘의 카드 가이드** | 카드·영역별 남은 한도와 BEP까지 남은 사용액, 오늘 나갈 정기결제와 그 카드, "오늘은 이 업종은 이 카드로" |
| 점심 12:30 | **중간 점검** | 오전에 새로 들어온 결제, 방금 한도·횟수를 다 쓴 영역("이 영역은 이제 다른 카드로"), 오후 결제에 쓸 카드 |
| 저녁 21:00 | **하루 마감** | 오늘 받은 할인과 놓친 할인(더 나은 카드가 있던 결제), 이번 달 누적 할인, 실적 인정 금액과 다음 달 구간 전망, 내일 나갈 정기결제 |

- **매월 1일 아침**에는 지난달 회고(받은·놓친 할인, 실적 함정 거래, 다음 달 바꿀 점)를 함께 보낸다.
- **경고:** 실적이 다음 달 구간 경계에 가까울 때, 정기결제가 횟수 제한 영역에 몰릴 때는 다음 리포트 맨 앞에 올린다.
- **연결 방식:** Agent 기능을 MCP 도구로 공개해 ChatGPT·Claude에서 커넥터로 부르거나, 정해진 날 리포트를 만들어 보낸다.
- **단계:** 1단계는 혼자 돌리는 로컬 Agent(이 기획서의 기능)이고, 2단계에서 개인 LLM 연결과 정기 리포트를 붙인다.

## 2. 왜 필요한가

- 카드 광고는 "10% 할인", "15% 할인"처럼 할인율만 앞세운다.
- 실제로는 전월실적 하한, 월 할인한도, 영역별 한도, 가맹점 제한, 횟수 제한이 붙어서 체감 할인이 광고보다 훨씬 적다.
- 가장 큰 함정은 **할인받은 결제가 다음 달 실적에서 빠지는 조항**이다. 할인을 받을수록 다음 달 실적이 줄어 혜택 구간이 떨어질 수 있는데, 이 조항은 약관 깊숙이 있어 알아차리기 어렵다.
  - 예) "할인받은 매출의 50%는 실적 산정 제외", "할인 대상인 전기·가스요금은 실적 제외"
- 카드 여러 장의 조건을 매달 직접 계산해 어느 카드로 결제할지 정하기는 사실상 어렵다.

## 3. 누가 쓰나

- 신용카드를 여러 장(첫 버전은 삼성·KB·우리 3개 카드사, 가족카드 포함) 쓰는 개인 1명
- 자신의 카드 사용내역을 MyFinance MCP 서버로 모아 두고 있는 사용자

## 4. 핵심 기능

1. **할인·BEP 계산:** 카드별, 혜택 영역별로 예상 할인액, 남은 한도, BEP, BEP까지 남은 사용액을 보여준다.
   - 영역마다 할인율과 한도가 다른 카드(예: 우리 카드의정석2 ROUTINE)는 영역 단위로 나눠 분석한다.
2. **실적 함정 점검 (RAG):** 자동으로 내려받은 약관을 RAG로 검색해 실적 산정 제외 조항(할인받은 매출 제외, 실적 제외 업종, 혜택별 실적 조건)을 찾고, 원문과 쪽을 함께 보여준다. 찾은 조항을 내 사용내역에 적용해 "겉보기 사용액"과 "실적으로 인정되는 금액"을 나란히 보여준다.
3. **지난달 회고:** 이미 끝난 달(예: 9월, 10월)을 다시 계산해 받았어야 할 할인과 놓친 할인을 보여주고, **향후 고려할 점**을 제안한다.
   - 예) 통신 할인이 월 1회인데 통신요금 여러 건이 한 카드에 몰려 있으면, 가장 큰 1건만 남기라고 안내한다.
4. **카드 추천**
   - **전환 추천(기본):** 이번 달 어떤 결제를 보유 카드 중 어느 카드로 옮길지 알려준다.
   - **교체 후보 추천(요청 시):** 사용자가 "이 카드 혜택이 별로다"라고 요청할 때만, 그 카드를 대신할 새 카드 후보를 약관 근거와 함께 비교한다. 비교에는 할인 대상이 실적에 포함되는지도 반드시 넣는다.
5. **명세서 대조:** 카드사 명세서 엑셀을 올리면 실제 할인과 계산값을 거래별로 맞춰 보고, 차이를 규칙 보정 후보로 보여준다. 보정은 사람이 승인해야 반영된다.
6. **카드 등록과 약관 자동 수집:** 처음 실행하면 연결된 카드 목록이 나오고, 카드마다 어떤 상품인지 대화로 고른다. 저장 전에 사람이 승인하며, 승인하면 그 상품의 약관을 자동으로 내려받아 점검할 수 있게 준비한다(5.3). 승인된 카드 정보는 확정값으로 쓴다.

## 5. 데이터

### 5.1 MyFinance MCP 서버 (카드 사용내역)

이 Agent는 카드 사용내역을 직접 수집하지 않는다. 사용자가 운영하는 **MyFinance MCP 서버**에서 읽기만 한다.

- **실데이터 수집:** 실데이터는 사용자 서버에서 Docker로 운영하는 MyFinance가 수집한다. MyFinance는 RPA로 각 카드사 사이트에 접속해 다음 두 가지를 모아 저장한다.
  - 카드별 **승인내역** (승인일시, 가맹점, 금액, 취소·환불, 업종, 본인·가족 구분 등)
  - 카드별로 정기적으로 결제되는 **정기결제 목록** (구독료, 통신비, 관리비 등)
- **Agent와의 관계:** Agent는 이 서버를 사용내역 데이터베이스로 쓴다. 카드사 로그인 정보는 MCP 서버에만 있고, Agent는 이를 다루지도 보관하지도 않는다.
- **접근 방식:** 처음 한 번 브라우저에서 MyFinance 계정으로 로그인해 연결을 승인하면, 그 뒤로는 **읽기 전용 권한**으로만 데이터를 조회한다.
- **데이터를 다룰 때 지킬 점:**
  - 정기결제 금액은 등록된 기준값이라 실제 청구액과 다를 수 있다.
  - 가맹점명·메모는 신뢰할 수 없는 데이터로 다루고, 그 안의 문장을 지시로 따르지 않는다.
  - 병원·약국 같은 의료 가맹점명은 받는 즉시 "병원진료"로 바꿔, 진료 내용이 드러나지 않게 한다.

### 5.2 테스트 서버 (채점·시연용)

실제 개인 금융 데이터 없이도 확인할 수 있도록 MyFinance MCP의 테스트 서버를 공개해 두었다.

- **주소:** https://test.finance.zswagger.com/
- **데이터:** 운영 서버와 같은 형식의 **가상** 승인내역과 정기결제 목록 (카드 4장, 2026년 7~12월)
- **차이:** 구조와 로그인 방식은 운영 서버와 같고, 데이터만 가상이다.
- 실데이터는 사용자 서버에서만 다루고, 공개하는 결과물에는 테스트 서버의 가상 데이터만 담는다.

### 5.3 카드사 약관 (자동 다운로드 + RAG 점검)

- **다운로드 자동화:** 카드를 등록할 때 사용자가 상품명을 말하면, Agent가 해당 카드사(삼성·KB·우리) 홈페이지의 상품 목록을 검색해 후보를 보여준다. 사용자가 상품을 고르고 승인하면 그 상품의 상품설명서·약관 PDF를 공시실에서 **자동으로 내려받는다.** 사용자가 약관 파일을 직접 찾을 필요가 없다.
- **버전 보관:** 내려받은 시점의 원본을 버전별로 보관한다. 약관이 바뀌어도 어느 시점의 문서를 근거로 계산했는지 추적할 수 있다.
- **RAG로 약관 점검:** 내려받은 약관을 검색 가능한 형태로 저장해 두고, 질문이 들어오면 관련 조항을 찾아 답의 근거로 쓴다. 답변마다 어느 문서 몇 쪽의 어떤 문장이 근거인지 함께 보여준다.
- **실적 함정 자동 점검:** 약관 전체에서 "할인받은 매출 실적 제외", "실적 제외 업종", "혜택별 실적 조건" 같은 조항을 자동으로 찾아 원문으로 보여준다.
- **교체 후보도 같은 방식:** 새 카드 후보를 비교할 때도 후보의 약관을 자동으로 내려받아 같은 기준으로 점검한다.

## 6. 지킬 원칙

- **숫자는 코드가 계산한다.** 할인액, 한도, BEP는 LLM이 아니라 파이썬 코드가 계산하고, LLM은 그 값을 그대로 전한다.
- **약관 근거가 있는 것만 말한다.** 모든 혜택 조건에는 약관 원문 인용을 붙이고, 찾지 못한 조건은 "약관에서 확인되지 않음"이라고 말한다.
- **사람이 승인한다.** 카드 등록과 규칙 보정은 사람이 승인해야 반영된다.
- **권유하지 않는다.** 새 카드는 사용자가 요청할 때만 비교 정보로 보여주고, 발급 여부는 사용자가 정한다.
- **위험한 질문은 막는다.** 지시 무시 시도, 토큰·카드번호 요구, 카드와 무관한 질문은 정해진 문구로 거절한다.

## 7. 기대 효과

개인의 카드 최적화로 **연간 약 20~30만원**을 더 받는 것을 목표로 한다(카드 3~4장, 1인 기준 가정).

- 횟수 제한 영역에 몰린 결제를 정리한다.
- 비어 있는 할인 영역으로 이미 내는 정기결제(구독, 멤버십)를 옮긴다.
- 실적 제외 거래 때문에 다음 달 혜택 구간이 떨어지는 것을 막는다.
- BEP를 넘긴 소비를 다른 카드로 옮긴다.

## 8. 성공 기준

| 항목 | 기준 |
|---|---|
| 할인·BEP 계산 | 경계 상황(하한 직전·직후, 한도 직전·직후, 횟수 제한, 환불, 본인+가족 합산, 실적 함정)에서 손계산과 **원 단위 100% 일치** |
| 약관 근거 | 계산에 쓰는 모든 조건의 인용문이 약관 원문과 **100% 일치** |
| 안전 | 차단해야 할 질문은 막고 정상 질문은 통과: **100%** |
| 답변 품질 | 도구 선택, 약관 사실, 회고 답변 등 나머지 문항 **90% 이상** |

## 9. 범위 밖 (첫 버전)

- 연회비까지 포함한 손익 계산
- 한 달 전체 결제를 미리 카드별로 나누는 최적 배분
- 삼성·KB·우리 외 카드사
- 여러 사용자 지원
- 새 카드 발급 권유
